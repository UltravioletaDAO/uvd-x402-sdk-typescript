# El SDK ahora elige el sobre; antes lo imponía

**Fecha:** 2026-09-03 · **Rama:** `0xultravioleta/sdk-sobre-v2` · **Versión:** 2.78.0 (sin publicar)
**Facilitador medido:** `https://facilitator.ultravioletadao.xyz` — versión **2.10.0**

---

## QUÉ / POR QUÉ / RIESGO

**QUÉ:** `FacilitatorClient.verify()` y `.settle()` ahora eligen entre el sobre v1 y el v2
en vez de mandar v1 siempre. Se agregó la conversión desde el `PaymentRequirements`
v1 que el SDK ya construye hacia el par `{resource, accepted}` de v2.

**POR QUÉ:** el SDK **anuncia v2 solo** (`createHonoMiddleware` → `resolveAdvertisedVersion`
devuelve 2 apenas hay dos accepts o uno con CAIP-2) y después era estructuralmente
incapaz de llamar al facilitador en v2. El pagador que hacía caso a ese 402 recibía 400.

**RIESGO:** que una llamada que hoy funciona cambie de forma. Se acotó midiendo primero:
la regla de auto se dispara **solo** en combinaciones que hoy ya son 400 duro.

## 1. El hallazgo que corrige el diagnóstico del despacho

El despacho decía que el SDK "solo sabe emitir v1". Medido, es más preciso y más grave:

`buildVerifyRequestV2` / `buildSettleRequestV2` **existen desde la v2.44.0**
(commit `e48af90`, 2026-07-29) y su forma **sigue siendo exactamente la que producción
acepta hoy** — lo verifiqué de nuevo. Lo que no existía era **cómo llegar a ellos**:

| | dónde | estado antes |
|---|---|---|
| builders v2 | `src/backend/index.ts:466-570` | ✅ existían, forma correcta |
| `FacilitatorClient.verify` | `src/backend/index.ts:729` (antes) | ❌ `buildVerifyRequest` fijo = v1 |
| `FacilitatorClient.settle` | `src/backend/index.ts:783` (antes) | ❌ `buildSettleRequest` fijo = v1 |
| conversión v1 → v2 | — | ❌ no existía; el consumidor la escribía a mano |

`verify`/`settle` son por donde pasan `createPaymentMiddleware`, `createHonoMiddleware`,
`verifyAndSettle` y toda integración de vendedor. **El SDK podía describir v2 y no podía
hablarlo.** Por eso MeshRelay estaba portando el arreglo desde su propio Turnstile: no era
un defecto de ellos, era que el único camino era hacerlo a mano.

### La suite del repo tenía el bug fijado como correcto

`src/backend/index.test.ts:300` asserteaba:

```js
expect(verifyRequest.paymentRequirements.network).toBe('eip155:1');
```

Ese cuerpo exacto, contra producción hoy, es **400**. El test montaba
`createHonoMiddleware` con dos accepts → el 402 sale en v2 con CAIP-2 (el test de arriba
lo assertea) → el pagador responde con `eip155:1` → y la suite verificaba que el SDK
mandara ese id CAIP-2 dentro del sobre v1. El `fetch` stubbeado nunca se enteró.

## 2. Las pruebas vivas (pegadas)

Todo lo de abajo es `POST /verify` contra producción, 2026-09-03. La firma es falsa
(`0xabab…`), así que el veredicto siempre es `isValid:false`; lo que discrimina es si el
facilitador **entendió** el cuerpo (200) o **no pudo leerlo** (400).

### 2.1 Qué acepta y qué no

```
### P1 sobre v1, exactamente lo que buildVerifyRequest() emite hoy
HTTP 200  {"isValid":false,"invalidReason":null,"payer":"0x7052cA44…402B"}

### P3 sobre v2, exactamente lo que buildV2Envelope() emite hoy
HTTP 200  {"isValid":false,"invalidReason":null,"payer":"0x7052cA44…402B"}

### P4 header v2 metido en el sobre v1  (lo que FacilitatorClient hacía)
HTTP 400  {"error":"Failed to deserialize VerifyRequest: data did not match any
           variant of untagged enum VerifyRequestEnvelope","code":"invalid_request_body"}

### P2 el ejemplo publicado en /skill.md, verbatim
HTTP 400  (misma deserialización fallida)

### P5 sobre v2 SIN repetir resource/accepted dentro de paymentPayload   → HTTP 400
### P6 sobre v2 con nombre plano en vez de CAIP-2                        → HTTP 400
### P7 sobre v1 llevando un network CAIP-2                               → HTTP 400
### P8 sobre v2 con maxAmountRequired en vez de amount                   → HTTP 400
### P9 sobre v2 con resource como string suelto                          → HTTP 400
### P10 sobre v2 sin resource/accepted en el top level                   → HTTP 400
```

En `/settle` el error es todavía más explícito sobre la causa:

```
### S3 /settle, header CAIP-2 en el sobre v1
HTTP 400  {"error":"Failed to deserialize SettleRequest: unknown variant `eip155:8453`,
           expected one of `base-sepolia`, `base`, `xdc`, `avalanche-fuji`, … "}
```

El enum de networks del sobre v1 **no contiene ninguna forma CAIP-2**. Ese es el
mecanismo exacto de la fricción de hoy.

### 2.2 Qué campos son obligatorios en v2 (medido, no deducido)

```
### Q1 accepted CON extra {name,version}          → HTTP 200   (pasa; EURC lo necesita)
### Q2 accepted CON outputSchema                  → HTTP 200   (claves de más se toleran)
### Q3 accepted CON sobras v1 (maxAmountRequired…)→ HTTP 200
### Q4 paymentPayload CON extensions:{}           → HTTP 200
### Q5 resource sin description/mimeType          → HTTP 400   ← las tres claves obligatorias
### Q6 accepted sin maxTimeoutSeconds             → HTTP 400   ← obligatorio
```

**Mínimo v2:** top level `{x402Version:2, paymentPayload, resource, accepted}`;
`paymentPayload` = `{x402Version:2, resource, accepted, payload}`;
`resource` = `{url, description, mimeType}` (las tres);
`accepted` = `{scheme, network(CAIP-2), asset, amount, payTo, maxTimeoutSeconds}` (las seis),
`extra` opcional. Coincide exactamente con los tipos `ResourceInfoV2` /
`PaymentRequirementsV2` que ya estaban en el repo.

### 2.3 La medición que cambió la decisión de diseño

Mi primer instinto fue disparar v2 cuando `paymentHeader.x402Version === 2`. **Medirlo lo
refutó:**

```
### M3 header con marcador x402Version:2 + nombres planos, en el sobre v1
HTTP 200  {"isValid":false,"invalidReason":null,"payer":"0x7052cA44…402B"}
```

El enum de sobres del facilitador es **untagged**: matchea por **forma** e **ignora el
marcador de versión**. O sea que un header que solo *declara* v2 llevando nombres planos
**hoy se sirve bien**, y subirlo por el marcador habría cambiado una llamada que funciona
— justo lo único que no había que hacer.

La tabla completa, sobre v1:

| network del payload | network de requirements | hoy |
|---|---|---|
| `base` | `base` | **200** |
| `base` (marcador dice `x402Version: 2`) | `base` | **200** |
| `eip155:8453` | `base` | 400 |
| `base` | `eip155:8453` | 400 |
| `eip155:8453` | `eip155:8453` | 400 (`unknown variant`) |

**Por eso `'auto'` se decide por CAIP-2, no por el marcador.** Toda combinación con CAIP-2
ya es 400 duro, así que pasarlas a v2 no puede regresionar a nadie: solo convierte una
falla en un pago. Y ninguna de las dos filas que hoy dan 200 se toca.

### 2.4 End-to-end: el SDK compilado contra el facilitador vivo

No son cuerpos escritos a mano — es `FacilitatorClient` construyendo el cuerpo:

```
### v1 sin cambios: nombres planos de los dos lados
   el facilitador entendió el cuerpo: SÍ (HTTP 200)   isValid=false invalidReason=null

### EL CASO MESHRELAY: el pagador repite el id CAIP-2 que anunció el 402
   el facilitador entendió el cuerpo: SÍ (HTTP 200)   isValid=false invalidReason=null

### requirements CAIP-2, header con forma v1
   el facilitador entendió el cuerpo: SÍ (HTTP 200)   isValid=false invalidReason=null

### header CAIP-2, requirements con forma v1
   el facilitador entendió el cuerpo: SÍ (HTTP 200)   isValid=false invalidReason=null

### control: x402Version pineado a 1 sobre un par CAIP-2 (tiene que seguir fallando)
   invalidReason=Facilitator error: 400 - {"error":"Failed to deserialize VerifyRequest:
   data did not match any variant of untagged enum …
```

El control cierra el argumento por los dos lados: prueba que el pin se respeta **y** que
los tres casos CAIP-2 estaban genuinamente rotos antes.

## 3. Qué se cambió

`src/backend/index.ts`

- `FacilitatorClientOptions.x402Version?: 1 | 2 | 'auto'` — default `'auto'`. Un pin se
  respeta aunque contradiga el cable: elegir la versión es el punto de la opción.
- `resolveEnvelopeVersion(header, requirements, requested?)` — la regla de §2.3.
- `buildVerifyRequestForVersion` / `buildSettleRequestForVersion`.
- `toResourceInfoV2` / `toPaymentRequirementsV2` — la conversión desde el
  `PaymentRequirements` v1 que el SDK ya construye. **Esto es lo que significa "el
  consumidor no escribe código"**: sigue pasando el objeto que ya tenía.
- `verify()` / `settle()` cablean lo anterior.

`buildVerifyRequest` / `buildSettleRequest` quedan **intactos**, con sus tipos de retorno
exactos. Ensancharlos a una unión habría roto a todo consumidor de TypeScript sin ganar
nada.

**Los tres renombres que hacen el daño** (y que el facilitador no nombra nunca):
`maxAmountRequired` → `amount`; `network` en CAIP-2; y `resource`/`description`/`mimeType`
salen a un **objeto** `resource`. `extra` viaja igual — ahí vive el dominio EIP-712 de los
tokens que el facilitador no conoce por dirección (EURC, los USDC puenteados); tirarlo los
haría impagables.

XRPL se queda en v1 y está bien: `xrpl-mainnet` no tiene forma CAIP-2, su string v1 **es**
su identificador.

## 7. Dos cosas para el facilitador (worker x4-implementa)

1. **`/skill.md` sigue devolviendo 400.** El ejemplo de `/verify` (sección 3) usa un
   `paymentPayload` plano `{signature, payload:{scheme,network,asset,from,to,amount,…}}`
   sin `authorization`. Medido hoy: **400**. Está copiado igual en `openapi.json`
   (`paths./verify.post.description`). Y el `hint` del propio 400 manda a `/skill.md`,
   así que el que se equivoca es derivado al ejemplo que no anda.
2. **Un token desconocido devuelve `internal_error`, no un 4xx limpio.** Con la forma v2
   correcta y un asset inexistente: `400 {"error":"internal_error (ref: …)"}`. Aislado:
   `eip155:1` con USDC real de mainnet → **200**; el mismo sobre con `0x2222…2222` →
   `internal_error`. O sea que es el token, no el sobre — pero el mensaje no lo dice.
   (`eip155:1` + USDC real en v2 dando 200 también confirma que esto no es solo de Base.)
